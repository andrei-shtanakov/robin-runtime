# Epic-axis shadow digest — дизайн (Ф5 ADR-ECO-010, срез 1)

Статус: draft · Дата: 2026-08-26 · Репо: robin-runtime

## 1. Контекст и цель

ADR-ECO-010 (`prograph-vault/authored/decisions/2026-08-25-adr-eco-010-epics-and-defect-classes.md`)
назначает robin плоскость **движения**: коммит-трейлеры `Epic:` / `Defect:`
отвечают на «что двигалось за окно» (D9). Ф5 по ADR — «сначала
shadow-сравнение, затем смена главной оси по достигнутому порогу»: недельный
дайджест, сгруппированный по репо, показывает один кросс-репный поток как
несколько несвязанных абзацев; ось эпиков должна это исправить, но менять
главную ось можно только по порогам `robin_cutover_*` (D8), а пороги
пересматриваются «после двух полных недель shadow-режима robin» (OQ-1).

Этот срез строит **shadow**: рядом с обычным weekly-дайджестом robin
детерминированно рендерит то же окно, сгруппированное по эпикам, и
персистит его — не публикуя в канал и не меняя командный продукт.

**Замер-вход (2026-08-26, окно 2 недели, 10 репо):** 0 machine-читаемых
трейлеров `Epic:` на ≈1000 коммитов. Ось движения сегодня пуста — и это
первое, что shadow обязан показывать честно: почти всё в bucket
`unclassified`, с растущей долей классифицированного по мере принятия
конвенции. Shadow — инструмент, который делает принятие видимым; он не
предполагает, что данные уже есть.

Второй факт из замера: трейлер, отделённый пустой строкой от финального
блока трейлеров (`Epic: x`, пустая строка, `Co-Authored-By: …`), git
**не считает трейлером** — `%(trailers)` его не видит. Это дефект записи
коммита, а не парсера; см. §5 про строгий разбор.

## 2. Не-цели

- **Cutover**: главная ось дайджеста не меняется; Telegram-выдача не
  меняется; LLM-промпт дайджеста shadow-данных не получает.
- **Плоскости состояния** (TODO / открытые issues / PR) — это dispatcher
  (D9); shadow их не читает и не показывает.
- **Enforcement**: валидация грамматики и эскалация EP-* — сенсор зонтика
  и продюсеры (Ф1b/Ф6). Shadow не пересчитывает и не дублирует их
  семантику; невалидное для него — просто bucket с примером, не ошибка CI.
- **Поход в GitHub API** — отвергнут ADR (второй коллектор).
- **Атрибуция commit→PR по snapshot/v2** — срез 2 (§8): канал доставки
  снапшотов в KB ещё строится (dispatcher#199), у robin на VPS свежего
  снапшота сейчас физически нет. Скелет модуля проектируется под второй
  источник, но в этом срезе его нет.

## 3. Архитектура

Новый модуль `src/robin/epic_shadow.py`. Детерминированный (ни одного
LLM-вызова): shadow — измерительный прибор для решения о cutover, его
выход должен быть воспроизводим и сравним между неделями. Канонический
порядок фиксируется: эпики и репо — по возрастанию ключа/имени, примеры
в bucket-ах — первые три по паре `(repo, sha)`, JSON пишется с
`sort_keys=True`. Одинаковый вход → побайтно одинаковый выход.

**Окно.** `run()` (`src/robin/digest.py:310`) сейчас не владеет окном:
`compose()` вычисляет `Period` внутри и не возвращает его, а `persist()`
сдвигает marker — повторный вызов `window()` после него дал бы новое,
почти пустое окно. Поэтому интерфейс меняется: `run()` получает сигнатуру
`run(kind, *, now=None)` и разыменовывает `now` в текущее время **ровно
один раз на входе**; это единственное `now` прогона — от него считаются
`Period`, `generated_at`, дата имён файлов, и его же инжектирует тест
детерминизма. `run()` вычисляет
`period = window(config, kind, now=now)` **один раз**, с пришпиленным
верхом (`until=now` вместо плавающего `None` — иначе коммит, успевший
между двумя проходами `git log`, попал бы только в shadow), и передаёт
его и в `compose(..., period=...)`, и в shadow. Один объект окна — оба
представления считаются по нему.

Запуск — из `digest.run("weekly")`, **последним шагом** `run()`: после
`persist()`, `post()`, `record_plan_state()` и success-record
(`src/robin/digest.py:313-331`) — чтобы ни доставка дайджеста, ни сдвиг
baseline дельты не оказались после прибора и не пострадали от его сбоя.
(Сбой Telegram в `post()` на shadow при этом влияет — прогон умрёт до
него; это принято: shadow без доставленного дайджеста не нужен, окно
пере-считается следующим прогоном.) Весь вызов shadow обёрнут try/except в `run()`: любое его
исключение логируется и **best-effort** пишется failure-record в
`interactions.jsonl` (`surface="epic-shadow"`); сбой самой записи
failure-record подавляется (при нечитаемом `var/` не запишутся ни
артефакты, ни record — сбой виден по логу systemd и по отсутствию
файлов). Основной дайджест не зависит от прибора ни на одном пути.

Данные (в этом срезе два источника):

1. **Трейлеры локальных коммитов окна.** Обход — тот же корпус, что у
   основного коллектора: `[config.vault_path, *config.repo_paths]`
   (`src/robin/changes.py:269`) — иначе vault выпадал бы из shadow,
   присутствуя в основной оси того же окна. Дополнительно провенанс
   обязан перечислить `config.missing_mirrors` как
   `skipped: not a directory`: `load_config()` молча фильтрует
   отсутствующие каталоги из `repo_paths` (`src/robin/config.py:149`),
   и без этого пропавшее зеркало исчезало бы из shadow бесследно.
   По каждому зеркалу — собственный read-only `git log` окна (таймаут и
   обвязка — как у `git_log`, `src/robin/changes.py:126`, но **без**
   `--no-merges`, который тот ставит на строке 139: shadow считает все
   коммиты окна, и merge-коммиты честно падают в `unclassified`).
   Framing — как у существующего коллектора (`changes.py:143`):
   `--format=%x1e%H%x1f%(trailers:key=Epic,valueonly=true)%x1f%(trailers:key=Defect,valueonly=true)`
   — записи по `0x1e`, поля по `0x1f`; многострочные значения трейлеров
   остаются внутри поля и режутся по `\n`.
   Состояния источника per-repo: git отсутствует / timeout / non-zero →
   зеркало в провенансе как `skipped: <причина>`, счётчики по нему не
   рисуются нулями; порог `MAX_COMMITS_PER_REPO`-типа shadow **не
   ставит** (лимита нет — это счёт, не промпт-бюджет; защита — только
   таймаут, его срабатывание = `skipped: timeout`). Нечитаемая запись
   формата (не разрезалась на 3 поля) → запись пропускается, зеркало
   помечается `partial: <n> unparsed` в провенансе.
2. **Реестр значений** — файл `epics.toml` в корне зеркала зонтика
   `ai-orchestrators-workspace`, секция `[epics]`: ключи = id эпиков,
   у каждой записи берётся только `title` (строка; отсутствует или не
   строка → ключ показывается без title). По ADR значения читаются
   живьём, не вендорятся. Чтение — stdlib `tomllib` (python ≥ 3.12),
   **всё-или-ничего**: ЛЮБОЙ сбой получения множества ключей — файла
   нет, `OSError`/`PermissionError` при чтении, ошибка декодирования,
   TOML parse error, `[epics]` отсутствует или не таблица — даёт реестр
   `unavailable` с причиной в провенансе и никогда не роняет shadow
   (catch-all вокруг чтения реестра). Частичного состояния нет
   намеренно: реестр — один маленький файл, а его потребление здесь —
   множество ключей и title; per-entry деградация не имеет потребителя. Зонтик добавляется
   в **оба** списка зеркал одним PR: `_ECOSYSTEM_REPOS`
   (`src/robin/config.py:26`) и `deploy/setup.sh` (`REPOS`) — двойной
   список, известная грабля репо; расхождение ловит
   `test_mirror_list_matches_the_deploy_script`.

## 4. Классификация коммита

Вход классификации — **множество непустых уникальных значений** `Epic:`
коммита: пустые значения отбрасываются, дубликаты одного значения
схлопываются (два одинаковых `Epic: eco.x` = одно значение). Дальше —
первый подошедший:

| уникальных значений | реестр | bucket |
|---|---|---|
| 1, ключ есть в реестре | read | этот эпик |
| 1, ключа в реестре нет | read | `unregistered` (ключ показывается) |
| 1 | unavailable | `unverified` (сырой ключ, без сверки) |
| ≥ 2 | любой | `conflict` |
| 0 | любой | `unclassified` |

- `Defect:` bucket не выбирает (класс ортогонален — ADR); счётчик `M` в
  строке эпика = число коммитов bucket-а, несущих **хотя бы один
  непустой** `Defect:`-трейлер; значение класса не валидируется —
  enforcement живёт у сенсора (§2).
- Merge-коммиты вида `Merge pull request #N` **не** исключаются и не
  разворачиваются: при merge-стратегии трейлеры несут коммиты ветки, и
  те из них, что сделаны в окне, присутствуют в `git log` сами;
  merge-коммит без трейлера честно падает в `unclassified`. Заявленные
  неполноты трейлерного источника (обе раскрываются в провенансе, §6,
  и не маскируются эвристикой по `#N` в subject — она отвергнута ADR
  D9): (а) коммиты ветки старше `since`, влитые мержем внутри окна, в
  окно `git log --since` не попадают; (б) трейлер, живущий **только в
  теле PR** (squash без переноса в сообщение коммита), из git-истории
  не извлекается. Обе закрывает срез 2 атрибуцией по `merged`-окну
  snapshot/v2 (`merged_at` в окне). Squash-коммит, у которого `Epic:`
  попал в финальный блок самого сообщения, классифицируется обычным
  путём.
- `unverified` при недоступном реестре — не молчаливая деградация:
  молча считать реестр пустым (всё → `unregistered`) запрещено, это
  выдало бы отсутствие прибора за находку. Строка `registry:
  unavailable` в провенансе обязательна.

## 5. Разбор трейлеров — строгий, git-семантика

Трейлеры извлекает сам git (`%(trailers:key=…)`), не grep по тексту
сообщения. Довод: grep узаконил бы записи, которые машинно трейлерами не
являются (замер §1: `Epic:` вне финального блока), и shadow показывал бы
покрытие, которого нет у остальных потребителей git-трейлеров. Дефект
записи должен быть виден как `unclassified`, чтобы его чинили в
конвенции коммита, а не прятали в каждом парсере заново. Регрессионный
тест фиксирует именно это поведение (§7).

## 6. Выход

Два файла за прогон из **одного** in-memory слепка (один расчёт — два
рендера, расхождение исключено построением):

- `var/epic-shadow/YYYY-MM-DD.json` — машинный:
  `{window, per_epic: {...}, buckets, provenance}` — материал для
  сравнения двух недель и решения OQ-1 о порогах. Формат внутренний
  (не контракт): потребитель — владелец и будущий cutover-анализ, обе
  стороны в этом репо.
- `var/digests/YYYY-MM-DD-weekly-epic-shadow.md` — человекочитаемый:
  окно, по строке на эпик (`<epic> «<title из реестра>» — N коммитов, M
  с Defect:, репо: a, b`), затем bucket-строки — **присутствуют и при
  нуле** (D10: исчезающая строка читается как «всё размечено» ровно
  тогда, когда данных нет): при реестре `read` это `unclassified` /
  `unregistered` / `conflict`, при `unavailable` — `unclassified` /
  `unverified` / `conflict` (`unregistered` без реестра не существует —
  сверять не с чем). Состав строк в JSON тот же. У
  `unregistered`/`unverified`/`conflict` — до трёх примеров
  `repo@sha <ключи>`; сырые значения при рендере в MD кодируются как
  JSON-строки (`json.dumps`) — однозначное экранирование без своих
  правил; у `conflict` — все уникальные значения коммита по
  возрастанию через ` + ` (`repo@sha "a" + "b"`; наборы `["a+b","c"]`
  и `["a","b+c"]` неразличимыми не будут). В JSON примеры — списком
  сырых строк, без кодирования. В конце блок провенанса: по каждому зеркалу
  `read` / `skipped: <причина>` / `partial: <n> unparsed`, состояние
  реестра, заявленные неполноты трейлерного источника (§4).

Порядок записи: сначала JSON, затем MD; оба с read-back-проверкой, как
`persist()` дайджеста (`src/robin/digest.py:269`). Атомарности пары нет,
принадлежность к одному слепку доказывается содержимым: оба файла несут
одинаковую метку слепка `generated_at` = ISO-времени `period.until`
(поле в JSON, строка в шапке MD) — не wall-clock записи, поэтому
детерминизм (§3) не нарушается: одинаковый вход, включая `now`, даёт
одинаковую метку; тест детерминизма инжектирует фиксированный `now`,
как остальные тесты дайджеста. Пара валидна, только если метки
совпадают. Смешанная пара (перезапуск
в тот же день перезаписал JSON, а MD упал и остался вчерашним по
содержанию) обнаружима по расхождению меток; сбой на любом из двух =
сбой всего shadow-прогона (failure-record, §3). Повторный weekly-запуск
в тот же день перезаписывает оба файла (идемпотентность по дате). В Telegram не постится ничего.

## 7. Тесты

Паттерн — tmp-git-фикстуры тестов `changes`. Обязательные случаи:

- трейлер в финальном блоке → классифицирован; трейлер, отделённый
  пустой строкой от финального блока → `unclassified` (регрессионный,
  обнажает дефект записи — фикстура строит оба коммита);
- два разных `Epic:` → `conflict`; два одинаковых → классифицирован
  (дубль схлопнут); пустое значение → отброшено; ключ вне реестра →
  `unregistered`;
- реестр недоступен → bucket `unverified`, строки `unregistered` нет,
  `registry: unavailable` в провенансе (и md, и json);
- merge-коммит без трейлера → `unclassified` (регрессионный к отличию
  от `git_log` с его `--no-merges`);
- реестр: параметризованный тест ВСЕХ классов сбоя §3.2 (нет файла,
  `OSError`/`PermissionError`, ошибка декодирования, невалидный TOML,
  нет `[epics]`, `[epics]` не таблица) → каждый даёт `unavailable`, не
  падение;
- зеркало с падающим git → `skipped: <причина>` в провенансе, прогон
  жив; запись, не разрезавшаяся на 3 поля → `partial: 1 unparsed`;
- окно пришпилено: коммит после `until` не виден shadow (и `run()`
  передал один `Period` в оба представления);
- ноль коммитов в окне → файлы всё равно пишутся: нулевые счётчики,
  все bucket-строки на месте, провенанс полный;
- детерминизм: два прогона по одной фикстуре дают побайтно одинаковые
  md и json;
- сбой shadow не роняет `digest.run` — основной дайджест персистится,
  failure-record записан; сбой записи самого failure-record подавлен;
- md и json согласованы (счётчики одного прогона совпадают — оба
  рендера одного слепка).

CI прежний: `uv run pytest -q`, `ruff format --check`, `ruff check src
tests`. Pyrefly в репо не настроен — не вводится этим срезом.

## 8. Срез 2 (не в этом PR)

Атрибуция commit→PR по окну `merged` из snapshot/v2: чтение
`derived/snapshots/<host>.json` из KB (ветка `derived-snapshots`),
сопоставление локальных SHA с `commit_shas`/`merge_commit_sha`,
классификация — **как опубликовал продюсер**, без пересчёта (D9);
v1-снапшот / отсутствие / протухание → явный `unavailable`/`stale`
в провенансе. Требует: канал доставки (dispatcher#199) и вендоринг
пиненой копии `contracts/snapshot/v2` с двумя гарантиями. Заводится
пунктом TODO с `@blocked_by` на dispatcher#199 (переходная форма
`<repo>#<номер>` — у dispatcher пункта-носителя в TODO ещё нет).

## 9. Приёмка среза

- Два подряд weekly-прогона на VPS дают оба артефакта; провенанс
  честный (список прочитанных зеркал совпадает с фактом).
- Через две полные недели shadow-режима — пересмотр порогов OQ-1
  (решение владельца, вне этого репо).
- Коммиты самого этого среза несут `Epic: eco.epics` корректным
  финальным блоком — первый вклад в собственный замер.
