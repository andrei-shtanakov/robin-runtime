## Грабли этого репо

- **Список зеркал живёт в двух местах** и обязан совпадать: `src/robin/config.py`
  (`_ECOSYSTEM_REPOS` — что Robin читает) и `deploy/setup.sh` (`REPOS` — что клонируется
  на VPS). Правишь один — правь второй, иначе репо есть в обзоре и отсутствует на диске
  (или наоборот). Оба уже разошлись так однажды: переименование `open-prose` → `libretto`
  (2026-07-16) обновило доки, но не списки.
- **Список задаёт имя каталога, а не наоборот** — и потому сам себя подтверждает.
  `setup.sh` клонирует явным таргетом (`git clone URL "$MIRRORS/$repo"`), так что каталог
  зовётся как запись в списке, независимо от имени репо на GitHub, а редирект со старого
  URL делает это бесшумным: `mirrors/open-prose` так и был **склонирован заново 2026-07-16,
  в день рейнейма**. Ручной `git clone <url>` дал бы `libretto` — и тогда список перестал
  бы резолвиться. Проверено 2026-07-26: и локально, и в `/srv/robin/mirrors` каталоги всё
  ещё `Maestro` и `open-prose`, поэтому команда и разработчик читают обзоры с разным
  составом репо.
- **Имя в списке = имя каталога после обычного `git clone`, то есть каноническое имя
  репо.** Иначе список становится машинно-зависимым: до #29 он держал `Maestro` и
  `open-prose`, и Robin был слеп к maestro и libretto на каждой машине, где каталоги
  назвал `git clone` — при том что на VPS они «работали» под мёртвыми именами. Один код,
  разный состав обзора, и ни одна раскладка об этом не сообщала. Расхождение двух списков
  теперь ловит `test_mirror_list_matches_the_deploy_script`, а вот несовпадение с реальными
  каталогами — нет (см. пункт про молчаливый фильтр).
- **Рейнейм зеркала: список и каталог — одним шагом.** Правка списка возвращает видимость
  на машинах с каноническими каталогами и ровно в тот же момент ломает раскладку, где
  каталог назван по старому списку (обычно VPS). Порядок, отработавший в #29: `mv` зеркала
  + канонический `remote set-url` → симлинк со старого имени, чтобы задеплоенный код не
  потерял репо до мержа → после деплоя симлинк убрать. Делать между прогонами дайджеста
  (таймер 09:00 Asia/Tbilisi) и подтверждать замером `open_items()` на VPS.
- **Непрорезолвившееся имя теряется молча:** `config.py` фильтрует записи через
  `.is_dir()`, поэтому опечатка или переименование убирают репо из обзора без ошибки,
  и отчёт о пробелах покрытия (#23/#24) этого не поймает — он работает внутри уже
  отфильтрованного списка. Пункт «перестать терять молча» — в `TODO.md`.
- **CD везёт только код.** Мерж в `master` → `deploy.yml` делает `git pull` + рестарт
  юнитов на VPS; `sync-mirrors.sh` (таймер) лишь `pull --ff-only` по **существующим**
  клонам. Новое зеркало нужно клонировать на VPS руками (или перезапустить
  `deploy/setup.sh` от root).
- **Теги планов не входят в ключ пункта.** Идентичность — «файл + прозаический текст без
  тегов» (`plan_state._key`), поэтому проставить `@owner:` соседу безопасно: дельта не
  отчитается о «закрыт/открыт». Ломает это только переформулировка самого текста.
- **`var/` — состояние Robin, не артефакт сборки:** снапшоты планов задают базовую линию
  дельты. Удаление файла её не подделывает (дайджест честно скажет «первая базовая линия,
  а не доказательство, что ничего не двигалось»), но каденция сравнения теряется.

## Git workflow (у репо есть remote)

- Ветка `<type>/<slug>` → push → `gh pr create`. **Прямые коммиты в `master`
  запрещены**, как и локальный мерж ветки в `master` в обход PR.
- После открытия PR — прочитать ревью **GitHub Copilot**: валидные замечания исправлять
  новыми коммитами в ту же ветку; невалидные — ответить с обоснованием, **не применять
  вслепую**; итерировать, пока не останется открытых замечаний. Ревью не всегда
  запрашивается само — если его нет, запросить явно:
  `gh api -X POST repos/<owner>/<repo>/pulls/<n>/requested_reviewers -f 'reviewers[]=copilot-pull-request-reviewer[bot]'`.
- **Не мержить.** Мерж делает пользователь.
- После мержа пользователем: `git switch master && git pull --ff-only`, затем удалить
  влитую ветку в **обеих половинах**: локально `git branch -d <ветка>` (после squash-мержа
  `-d` откажется — сверить, что `git diff master <ветка>` пуст, и удалить
  `git branch -D <ветка>`) и на origin
  `git push origin --delete <ветка>`, если GitHub не удалил сам; затем `git fetch --prune`.
- Никогда не делать force-push в общие ветки; не трогать другие репо (см. scope выше).
- Полное правило (SSOT): `../prograph-vault/authored/rules/git-workflow.md`.

## Входящие запросы (inbox)

В начале работы проверь входящие: `gh issue list --label inbox --state open`.
Issue с лейблом `inbox` — запрос от соседнего репо, ещё **не** пункт плана.
Принять = завести пункт в `TODO.md` с указанным `slug:`; принял под другим
именем — поправь `slug:` в теле issue.
Отказать = `gh issue close --reason "not planned"`.
Нужна работа в соседнем репо — не редактируй его: заведи там issue
(`slug:` + `from:` + проза). Правило: ADR-ECO-006 — канон в `ecosystem-kb`
(каталог `prograph-vault/` в корне воркспейса),
`authored/decisions/2026-07-28-adr-eco-006-cross-repo-issue-inbox.md`.

Исходящее ожидание — вторая половина того же ритуала: «ждём соседа» существует
**только** как чекбокс `TODO.md` с `@blocked_by:todo://<repo>/<id>` (переходно —
`<repo>#<номер>`); память сессий, заметки и handoff-доки — лишь зеркало. Находка
PF-BLOCKER-STALE по этому репо = «ожидание доставлено — действуй или переставь тег».
Правило (SSOT): `../prograph-vault/authored/rules/cross-repo-waits.md`.
